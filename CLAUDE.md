# Poop a Big Poop

3D park game. Vite + React 18 + @react-three/fiber 8 + three 0.171 + zustand, plain JS/JSX. Same architecture as ../Stone-Skipping.

- `npm run dev` / `npm run build`; `.env.example` documents `VITE_DEV_MODE` (skips the Bloxity SDK/CDN).
- `systems/` is framework-free (no React); all SDK calls go through `systems/bloxity.js` and must never throw.
- World layout lives in `data/world.js` (metres, +X east, +Z south): a floating 20-gon island, radius 26, with every prop position and the `OBSTACLES` collision circles. Surfaces use `materials/tile.js` (world-space checker + grout + `mottle` noise shader); procedural canvas textures (sky, pad swirl, signs) live in `utils/textures.js`.
- `LANDMARKS.md` names every island prop and HUD element (with position, world.js constant and component); use those names and keep it updated when props move or are added.

## Multiplayer / saving
All Colyseus traffic goes through `systems/net.js` (server: `../Poop-a-big-poop-backend`, `lobby` room); it never blocks gameplay when the server is absent. `VITE_SERVER_URL_DEV` / `VITE_SERVER_URL_MAIN` (repo variables `SERVER_URL_DEV` / `SERVER_URL_MAIN` in the deploy workflow) pick the URL. `move` relays position, yaw, gait and `grounded`; `components/RemotePlayers.jsx` renders every other session with the same character as `Player.jsx` (+ `Nametag.jsx`). Signed-in players are saved (`saveProgress`, debounced) and restored (`progress`): money, lifetime counters, the poop inventory (`poop.js` `getProgress`/`hydrate`), the daily boost (`boost.js`) and the Save Food Effects stall (`foodFx.js`) and the first-run tutorial step (`tutorial.js`, `tutorialStep` 0-5, 5 = done: the server only raises it and resumes the player there, `eat` resuming at `buy` since the pantry isn't saved; `tutorialDone` is still sent; accounts with earnings and no saved step count as done). The tutorial (`data/tutorial.js` steps, `components/Tutorial.jsx` banner) advances on game events, waits for a signed-in player's saved flag before showing, keeps a guest's in localStorage, and `VITE_NO_TUTORIAL=true` disables it. The pantry is deliberately not saved, since surviving a reload is what Save Food Effects sells. Saves wait until the server has answered (`progress`/`noProgress`), so starting values never overwrite a save. No poop-drop event is synced (the world `poops` array is not filled), and the Cliff Board doesn't draw `subscribeLeaderboard` data yet. Holding E within `STEAL_RANGE` of a remote player who holds poop (`poopCount` in the synced state, sent with `stats`) robs them for `STEAL_COST` ($1000, `data/net.js`): `systems/net.js` `requestSteal` pays up front and sends `steal`; the server checks reach/money/cooldowns, asks the victim's client (`stealRequest`) to hand its inventory over (`stealHandover`) and answers the thief with `stealResult` (failure refunds). The inventory is client-held, so the server only brokers the transfer; the victim is protected for 30 s afterwards. Holding E at the Locked Jar buys Theft Immunity (`systems/theftImmunity.js`, `JAR_COST` $1000): the buyer can't be robbed and can't rob. It's saved as `theftImmune` (one-way, in `saveProgress`/`progress`, Mongo `PlayerDoc`) and synced live as `PlayerState.immune` via `stats`, which the server's `steal` checks (`immune`); a guest keeps it for the session only. After A robs B, B can't rob A back for `STEAL_REVENGE_BLOCK_MS` (5 min, backend only, keyed by account id else session id, in room memory): the server sends the victim `stealBlock { target, ms }` (and `stealResult` reason `revenge` + `ms` if they try), and `interact.js` shows "Can't steal back from X · m:ss" in place of the steal prompt.

## Treasure Chest
`CHEST_ENABLED` (`data/world.js`, and the backend's `constants.ts`) is the master switch: when false the chest is hidden (nothing drawn, no E zone, no collision) and `openChest` is refused. Keep both in step.
Hold E at the Treasure Chest (`systems/chest.js`, `CHEST` in `data/world.js`). The first player opens it for everyone: the server broadcasts `chestAnim` so every client plays the opening, and it stays open until the server restarts (late joiners see it already open; `chest` carries `left`, `mine`, `open`). Every other player then redeems with E. Each claim (opener or redeemer) is broadcast as `chestClaim { id }`, and every client flies a stream of gold coins from the chest to that player (`components/TreasureFlight.jsx`, target = our own position or the remote player's). Only `CHEST_MAX_OPENS` (5) players ever get the prize (the opener counts), once each: $2,000 + a Glazed Donut. The server decides (`openChest` → `chestResult`); a signed-in claim is saved as `PlayerDoc.chestOpened` (never accepted from `saveProgress`), a guest's lasts the session, and with no server it opens once per session. Keep `CHEST_MAX_OPENS` in step with the backend's `constants.ts`.

## Forced update
The client sends `CLIENT_VERSION` (`data/net.js`) when joining; the backend's `MIN_CLIENT_VERSION` (`constants.ts`) is the lowest it accepts. An older client gets a `reload` message: `systems/net.js` saves progress, `systems/updateNotice.js` + `components/UpdateNotice.jsx` show a 5 s "New version available" banner and reload the page (a second request within 2 minutes asks for a manual refresh instead, so a host still serving the old build can't loop). To force everyone onto a deploy, raise both numbers together; leave them alone for deploys stale tabs can live with. Tabs from before this handshake send no version and can't act on it, so they need one manual reload.
